## 1. 背景与问题起点

M4-01-ID 定义了 message identity 契约（见 `src/server/workbenchos/ports/browserAutomationPort.ts` 顶部注释，contract FROZEN v0.1）：

```text
stable            : 同一 logical message 多次 observe 得到同一 message_ref
unique            : 同一 conversation 内不同消息得到不同 message_ref（即使内容相同）
consistent        : submitUserMessage 的 receipt.message_ref == 后续 observe 的 message_ref
since_fingerprint : 只影响返回范围，绝不改变任何 message_ref
fail closed       : identity 不确定时必须失败，禁止任何猜测式 fallback
```

第一阶段（READ-ONLY 设计审查）判定 M4-01-ID 为 **BLOCKED — CODE DEFECT**，发现 3 个实现缺陷。第二阶段修复缺陷。第三、四阶段在**真实 Chrome** 上完成 E2E 验证。

## 2. M4-01-ID：缺陷与修复

### 2.1 审查发现的 3 个缺陷

| 编号 | 位置 | 缺陷 |
|---|---|---|
| DEFECT-1 | `adapter.ts` observe 路径 | `m.id === ""` 时仍生成 `chatgpt:user:` 这类「看起来合法」的空 ref，无 fail-closed |
| DEFECT-2 | `adapter.ts` submit 确认路径 | 多个新 user 消息时用 `.find()` 取**第一条**（猜测式认领） |
| DEFECT-3 | `adapter.ts` observe 路径 | 同一 observation 内重复 stable id 未检测，破坏 uniqueness |

### 2.2 修复方式（`desktop/electron/chatgptBrowser/adapter.ts`）

- 新增 `assertStableIdentities()`（约 `:224-243`）：observe 后统一校验，任一消息 `id` 为空或 id 重复即抛 `UNAVAILABLE`，**不 synthesize 任何 ref**。
- submit 确认改为候选集合（`:195-208`）：
  - `candidates.length === 0` → `UNAVAILABLE`（发送未确认）
  - `candidates.length === 1` → 认领
  - `candidates.length > 1` → `UNAVAILABLE`（歧义，拒绝猜测）
- 候选筛选同时要求 `m.id.length > 0`、内容指纹匹配、且 `m.id` 不在发送前的 `beforeUserIds` 中。
- `message_ref` 统一为 `chatgpt:${role}:${m.id}`（observe `:93` 与 receipt `:247` **同源**），彻底移除 index / 位置 / 纯内容指纹派生的 ref。
- **Core 侧不变**：`message_ref` 对 Core 仍是不透明字符串。

**已验证事实**：Fake 无法产生空 id / 重复 id，因此这两条 fail-closed 分支在离线测试中由**受控 mock driver** 构造 `DriverRawMessage` 直接覆盖（未修改 Fake 的正常 identity 生成规则）。

## 4. M4-03B-FIX：recovery 误采纳修复

### 4.1 原始缺陷

`workbenchCore.ts` 的 `recoverOneBrowserSubmit()` 旧逻辑：

```ts
const settled = observation.messages.find(
  m => m.role === 'user' && m.content === intent.content && m.settled,
)
```

若会话中已存在历史 user 消息 `H` 且 `H.content === intent.content`，而本次操作的发送 `K` 已在 receipt 持久化前 crash，restart recovery 时的 `.find()` 可能认领 `H`，把历史消息当作 `K` 的 receipt —— **correctness defect**。

### 4.2 修复后的 recovery 算法

`workbenchCore.ts:1405-1444`：

```ts
const userMessages = observation.messages.filter(m => m.role === 'user')
const candidates = userMessages.filter(
  m => m.settled && m.content === intent.content && !baseline.includes(m.message_ref),
)

candidates.length === 1                                -> 恢复该条 receipt（Crash C，不重发）
candidates.length > 1                                 -> fail closed（INTEGRITY_FAILURE）
candidates.length === 0 && userMessages.length > 0    -> fail closed（不重发、不乱认）
candidates.length === 0 && userMessages.length === 0  -> 恰好一次重发（Crash B，语义不变）
```

**ownership 边界 = `message_ref ∉ pre_submit_baseline`**，内容匹配只是必要不充分条件，**绝不用 content fingerprint 代替 identity**。全程无 `.find()`、无 first/last/nearest 猜测。

### 4.3 baseline 的产生与持久化

- `submitBrowserUserMessage`（`workbenchCore.ts:518-548`）在 **提交 intent 之前**先做一次 `observeConversation`，收集当前 user 消息的 `message_ref` 集合写入 `intent.baseline_user_message_refs`。
- 该 observe 失败 → 直接 fail closed，**不落 intent、不产生外部副作用**。
- `parseBrowserSubmitIntent` 解析该字段。**「字段缺失」与「baseline 合法为空」被刻意区分**：缺失时返回 `undefined`（而非 `[]`）。
- `recoverOneBrowserSubmit` 在 **任何 observe / 重发之前** 检查 baseline 是否存在；缺失即 `INTEGRITY_FAILURE` fail closed（无外部往返开销）。
- 存储位置：既有 `outcome_ref` JSON 字符串列，**无 SQLite DDL 变更、无 migration**。

### 4.4 新增/更新的测试（`workbenchCore.browserRecovery.test.ts`）

| 用例 | 覆盖点 | 结果 |
|---|---|---|
| Case A | 历史 `H="SAME"` + 新发 `K="SAME"`，ack 丢失后 recovery 必须认领 `K`（`=== K.ref` 且 `!== H.ref`），且不重发 | PASS（**旧代码下会失败**，真正覆盖原 bug） |
| Case B | baseline=[H]、observation=[H]（无新候选）→ fail closed，不重发，record 保持 `reserved` | PASS |
| Case C | baseline=[H]、新候选 [K1,K2] → fail closed，绝不取第一条 | PASS |
| Case E | 历史 `H="OLD"`、intent `"NEW"` → 认领 `K`，不误认 `H` | PASS |
| Case F（legacy） | 修复**之前**落库、完全没有 `baseline_user_message_refs` 的 `reserved` 记录 → fail closed，**不退回仅内容匹配**、不认领 `H`、不重发，record 保持 `reserved` | PASS |
| 既有 Crash A/B/C、normal persistence、replay、same-content-different-key、unavailable/timeout、fingerprint mismatch、wrong conversation | 回归 | 全部 PASS |

`seedReserved` 测试辅助已扩展为携带 `baseline_user_message_refs`。

### 4.5 保持不变的语义（逐条确认）

- `approval_ref` 仍是 business approval evidence；**未**映射为 `bypassPermissions` 或任何 CLI permission bypass。
- 幂等仍为 **operation-level `idempotency_key`**；`content` / `content_fingerprint` / `message_ref` **未**被当作全局去重键（`same content + different idempotency_key` 仍可合法发送两次，该测试仍通过）。
- 未实现 Round Loop、未实现自动 retry、未改 `external_browser_submit` 业务语义。
